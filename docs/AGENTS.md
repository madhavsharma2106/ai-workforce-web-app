# Agents

How a Role (see [ROLES.md](ROLES.md)) becomes a running employee — model access, system prompts, tools, delegation, and background execution. This covers the platform; each role's own tools and business logic are documented in that role's file under `roles/`, not here.

## Model access

All employees run on Anthropic Claude for MVP, via the Vercel AI SDK. The only place a provider package is imported is `src/lib/agents/model.ts` (`getModel()`) — every call site gets its model through this function, never by importing `@ai-sdk/anthropic` directly, so adding a second provider later is a change in one file, not a rewrite.

LangChain is deliberately not used — its chain/memory/agent-executor abstractions don't add anything over the AI SDK + plain SQL here, and LangChain's own team steers people toward LangGraph for agents now anyway. `src/lib/agents/runTurn.ts` is the one place the per-turn agent loop is built, but AI-SDK-specific surface isn't fully contained there: `src/lib/agents/tracing.ts` wraps the AI SDK directly for LangSmith tracing, `src/lib/businessProfile.ts` and `src/lib/onboardingQuestions.ts` call AI SDK's `generateObject` directly (bypassing `runTurn.ts` entirely), and `graph.ts`'s LangGraph state schema is typed against AI SDK's `ModelMessage`. Tool definitions use the Zod-schema-plus-function shape LangChain's `tool()` also uses, but it isn't a literal drop-in — LangChain's signature is positional (`tool(func, { name, schema, ... })` vs. AI SDK's single-object `tool({ inputSchema, execute })`), requires each tool to self-declare a `name` (today inferred from its key in `toolsByRole.ts`'s registry), and coerces results to a string for the model by default rather than passing structured output straight through. A future move to LangChain, if ever needed, is a multi-file migration — tools, the tool registry, `graph.ts`'s state schema and step-narration logic, the two `generateObject` call sites, and `tracing.ts` — not a single-module swap.

## System prompts

Loaded at request/job time from `roles/<role>.md` (`src/lib/roles.ts`) — git stays the source of truth, not the DB. `src/lib/agents/systemPrompt.ts` composes: the role file verbatim, the employee's display name (`ROLE_LABELS`), `business_profiles.profile_md`, the voice/tone rules from [UX.md](UX.md) (the model doesn't default to first-person, matter-of-fact, no-hedging on its own — it has to be told), and the role's Do Not list. Boundaries are enforced structurally where possible, not just by prompt — e.g. Lead Sourcer's "Do Not: Send emails" means no `send_email` tool is ever defined.

## Tools

Each role has a tool registry in `src/lib/agents/toolsByRole.ts` (`Record<EmployeeRole, Record<string, Tool>>`) — the seam for adding role-specific tools later without touching the runtime. Tools live in `src/lib/agents/tools/`, one file per concern. Every role gets `delegate_to_employee`; the Lead Sourcer additionally gets `search_leads` (Apollo search + company research), `save_lead`, `note_passed_candidates` (documents why candidates it didn't qualify were passed on, so the founder can see every candidate was actually reviewed — see `docs/QUALITY.md`), `ask_account_manager`, and `web_search`; the Sales Representative gets `draft_outreach_email` or `draft_reply_email`, scoped to whichever lead its run was seeded for and disambiguated by the run's `jobKind` (see below) — never both in the same run, so a reply-drafting run can't accidentally overwrite the original outreach draft or vice versa — plus `ask_account_manager` and `web_search`. `web_search` (both roles) is Claude's built-in server-side search via `@ai-sdk/anthropic`'s `anthropic.tools.webSearch_20260209`, capped at `maxUses: 2` per turn — see `src/lib/agents/model.ts`; no separate search API/key. The Lead Sourcer originally didn't get `web_search` — her `search_leads` loop already fans out per candidate, and stacking open-ended search onto that seemed likely to multiply cost without a proven payoff. That's since been reversed: the per-turn cap already bounds it regardless of fan-out size, and her role guidance (`roles/lead-sourcer.md`) restricts her to using it only on candidates she's actually about to save — to surface a real "why now" trigger event (funding, a leadership change, a launch) — not on every candidate she looks at.

`ask_account_manager` (`src/lib/agents/tools/askAccountManagerTool.ts`) is a synchronous query, not a handoff: its `execute()` runs a second, nested, tool-free one-step turn as the Account Manager (`buildSystemPrompt` + `createEmployeeAgent`) and returns his answer text as the tool result, so the calling employee gets it back within the same turn and can act on it — unlike `delegate_to_employee` below, no `graph.ts` routing is involved, and it's scoped one-way (only Emma/Oliver can ask Alex; he's the only role today whose job is holding answerable knowledge).

## Delegation — LangGraph.js

Employees hand work to each other through a LangGraph `StateGraph` (`src/lib/agents/graph.ts`), one node per role. A node loads its role's system prompt + tools and calls `runEmployeeTurn` (AI SDK) for its own reasoning/tool-calling — LangGraph only governs what happens _between_ employees, not within one employee's turn.

Calling `delegate_to_employee` doesn't fire anything directly; it records a handoff request that the node wrapper turns into LangGraph's `Command({ goto: to_role, ... })`, routing execution to the target node within the same graph run. Cycles are bounded by LangGraph's `recursionLimit`. Each handoff is also logged to a `delegations` row (see [DATABASE.md](DATABASE.md)) as a framework-independent audit trail — LangGraph's own checkpoint history could technically reconstruct this, but it's serialized internal state meant for replay/debugging, not a stable, queryable product record.

There's a second, app-triggered path into this same machinery: approving a lead on Emma's page (`PATCH /api/leads/[id]`) fires a `leads/approved` Inngest event rather than a live `delegate_to_employee` tool call, because the handoff is founder-triggered and can happen long after Emma's graph run already finished — there's no live run to call the tool from. `src/lib/inngest/functions/draftOutreachOnApproval.ts` inserts the `delegations` row itself and starts a fresh graph run via `src/lib/agents/runGraphJob.ts` (the shared helper every Inngest function uses to resolve employees and call `graph.invoke()`), seeding `pendingDelegationId` directly in the initial state so `makeEmployeeNode`'s existing linking logic completes it exactly as it would for a live mid-run handoff, and seeding `leadId` so `getToolsForRole` can bind `draft_outreach_email` to that one lead.

A third path exists for reply monitoring: `src/lib/inngest/functions/pollForReplies.ts` (cron-triggered, see below) detects a genuine reply and fires `leads/reply-received`, which `src/lib/inngest/functions/draftReplyOnReceipt.ts` picks up the same way — inserting a `delegations` row (self-delegation, Oliver to Oliver, since no other role is involved) and calling `runGraphJob` with `leadId` and `jobKind: "reply"` set, so `getToolsForRole` binds `draft_reply_email` instead of `draft_outreach_email` for that run.

**Optional debugging aid — LangSmith.** Since graph nodes are LangChain `Runnable`s under the hood, setting `LANGSMITH_TRACING=true` + `LANGSMITH_API_KEY` (see `.env.example`) automatically traces every `graph.invoke()` to the LangSmith dashboard — no code changes, purely opt-in, the app behaves identically with these unset. Separately, `src/lib/agents/tracing.ts` wraps the AI SDK itself (`wrapAISDK`, from the `langsmith` package) so every `ToolLoopAgent`/`generateObject` call — including the underlying Claude call and tool arguments — is also traced, tagged with per-call metadata (`role`, `runId`, `employeeId`, etc.). These land as two separate trace trees today, not one nested hierarchy: the graph-node trace shows which role ran and state in/out, while the AI-SDK trace shows the Claude-call/tool-argument detail, and LangSmith doesn't automatically link the two. For a single, product-appropriate view of one run's activity, use `agent_run_steps` (below) instead.

## Making work visible: "Thinking" and handoffs

No raw model reasoning is shown to users. Claude's extended-thinking mode isn't enabled, because its tone/verbosity can't be controlled to match [UX.md](UX.md)'s voice rules. Instead, "Thinking" (the UX.md term for this) is synthesized narration: `src/lib/agents/narration.ts` maps each tool name to `before`/`after` copy, written once when a step is persisted to `agent_run_steps.label`. Every new tool needs a narration entry or it falls back to a generic label — an ongoing authoring cost, not a one-time setup. A handoff's explanation comes from the model-written `reason` argument on `delegate_to_employee`, constrained by its schema description to read as something a founder could see directly, not internal justification.

## Background execution — Inngest

Turn-based chat (a user actively talking to an employee) stays synchronous/streamed — one HTTP request per turn (`src/app/api/employees/[id]/chat/route.ts`, AI SDK `streamText` + `useChat`). Autonomous or multi-step work — anything that can involve a tool loop and/or a delegation — runs as a background job instead: one Inngest job = one LangGraph graph run, triggered by the `employee/run.requested` event (`src/lib/inngest/functions/runEmployeeGraph.ts`, a free-text debug/manual entry point), the `leads/approved` event (`src/lib/inngest/functions/draftOutreachOnApproval.ts`, the founder-triggered Emma-to-Oliver handoff), or the `leads/reply-received` event (`src/lib/inngest/functions/draftReplyOnReceipt.ts`, the poll-detected reply handoff) — with progress persisted to `agent_runs`/`agent_run_steps` and watched live via Supabase Realtime rather than polling or `sessionStorage`. Two events aren't graph runs at all — `leads/send-requested` and `leads/reply-send-requested` (`sendOutreachOnApproval.ts`/`sendReplyOnApproval.ts`) are deterministic Microsoft Graph API calls fired when the founder approves a draft, so they don't need a LangGraph node of their own. `pollForReplies.ts` is the first cron-triggered (not event-triggered) Inngest function in this codebase — it sweeps every connected mailbox on a schedule and is what actually fires `leads/reply-received`.

Inngest jobs run with no user session, so they use a service-role Supabase client (`src/lib/supabase/admin.ts`, server/job-only) that bypasses RLS — job code must filter every query by `user_id`/`employee_id` itself; nothing does this for it.

## Current status

This is platform infrastructure, not finished role behavior. The Account Manager, Lead Sourcer, and Sales Representative all have real graph nodes now. The Lead Sourcer calls `search_leads` (Apollo search + company research, bundled into one tool call since neither step has a judgment call in it — see `src/lib/agents/tools/searchLeadsTool.ts`) and then `save_lead` to persist each company it qualifies, with a fit reasoning grounded in the returned research. Once the founder approves a saved lead, the Sales Representative (see [roles/sales-representative.md](../roles/sales-representative.md)) is handed off to automatically and calls `draft_outreach_email` to write a personalized draft for founder review. Approving that draft (`draftStatus: 'approved'`) now sends it for real, from the founder's own mailbox via Microsoft Graph (`src/lib/integrations/email/outlook.ts`). Reply monitoring is also live: a cron job polls each connected mailbox for replies on threads Oliver sent, filters out obvious auto-replies/bounces, and hands genuine ones to the Sales Representative to draft a response with `draft_reply_email` — approving that (`replyStatus: 'approved'`) sends it threaded via Graph's reply endpoint. Each remaining role's actual tools, persistence, and UI land in that role's own follow-up pass — check `roles/<role>.md` for what a given role can actually do today versus what's planned.
